## 1. Why visibility is the next question（为什么下一步是可见性）

The platform may know a person's early co-building history（早期共建历史）, but not every historical record should automatically be public.

The next product question is:

> **What should the user see privately, what may be shown publicly, and what should remain internal/provenance-only?（哪些历史应由本人私下可见，哪些可以公开，哪些应只保留在内部 / 溯源层？）**

---

## 2. Proposed three-layer presentation model（建议三层呈现模型）

### Layer A — Private Personal History（个人私有历史）
Visible to the user/account owner.

Possible contents:
- complete early co-building timeline（完整早期共建时间线）;
- detailed support history（详细支持历史）;
- product testing / feedback history（产品测试 / 反馈历史）;
- project/recovery participation records（项目 / 寻回参与记录）;
- evidence/provenance explanation（证据 / 来源说明）.

This can be richer than the public profile.

### Layer B — Optional Public Historical Acknowledgment（可选公开历史致谢）
User may choose whether selected history appears publicly.

Possible examples:
- “Early Participant（早期参与者）”;
- “Founding-stage Co-builder（创始阶段共建者）”;
- selected milestone or project acknowledgment（部分里程碑 / 项目致谢）;
- visible join-era / founding-era marker（加入阶段 / 创始阶段标识）.

Public display should explain history, not imply expertise/authority.

### Layer C — Internal Provenance / Sensitive Records（内部溯源 / 敏感记录）
Some evidence may need to remain internal or access-limited:
- exact financial support amounts（具体资金支持金额）;
- private bug/security reports（私密问题 / 安全报告）;
- sensitive project evidence（敏感项目证据）;
- private identity/contact records（私密身份 / 联系记录）;
- internal moderation or verification context（内部审核 / 验证上下文）.

These should never be exposed merely to prove co-building.

---

## 3. Public display should be user-controlled（公开展示应由用户控制）

A strong default candidate is:

> **Historical recognition may exist even if the user chooses not to display it publicly.（历史承认可以存在，即使用户不选择公开展示。）**

This prevents forced public identity/status signaling.

---

## 4. Avoid badge stacking（避免徽章堆叠）

Early Co-builder（早期共建者） history should not create a status pile such as:

Verified + Contributor + Partner + Recognized + Founding + Member（已验证 + 贡献者 + 合作方 + 高认可 + 创始 + 会员）

on every content card.

Prefer:
- profile/detail surfaces for fuller context（个人资料 / 详情页呈现完整上下文）;
- only contextually relevant markers on feed/content cards（信息流 / 内容卡只显示必要标识）.

This follows the existing anti-prestige-stacking architecture（反身份堆叠架构）.

---

## 5. “Spiritual Shareholder（精神股东）” public language needs care（“精神股东”公开用语需要克制）

If used publicly, it should:
- feel playful / relational（有亲近感 / 社区感）;
- clearly avoid legal-equity implications（明确避免法律股权含义）;
- not imply that all Early Co-builders（早期共建者） share identical histories;
- not become an exclusive elite club（排他精英俱乐部）.

Public naming remains separate from backend architecture.

---

## 6. Current decision questions（当前决策题）

1. Should a user's full Early Co-builder（早期共建者） history be primarily available in a private personal view?
2. Should public historical acknowledgment be optional rather than forced?
3. Should sensitive evidence (amounts, private reports, private project details) remain internal even when the history itself is publicly acknowledged?
4. Should full historical context live mainly on profile/detail surfaces rather than feed/content cards?
5. Should “Spiritual Shareholder（精神股东）” remain an optional community-facing expression, while precise typed histories remain the real underlying record?
