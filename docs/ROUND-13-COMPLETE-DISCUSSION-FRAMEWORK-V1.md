# 0. Round 13（第十三轮）到底要解决什么

Round 13（第十三轮）不是“给旧服务找地方”，也不是“给 Project 3（项目三）强行设计收入来源”。

它要解决五个更基础的问题：

1. Project 3（项目三）哪些部分天然属于商业交易；
2. 哪些服务概念是真实产品，哪些只是旧页面遗留；
3. Ink & East（内容 / 知识产品域）与 Spatial Flow（商品 / 空间产品域）在同一平台中的关系；
4. 金钱可以影响什么、绝对不能影响什么；
5. 不同商业模式应该是一次性交易、服务收费、未来订阅，还是根本不该收费。

Round 13（第十三轮）的正确顺序必须是：

```text
Commercial role inventory（商业角色盘点）
→ Product-domain relationship（产品域关系）
→ Legacy service revalidation（旧服务重新验证）
→ Commercial boundary（商业边界）
→ Transaction / pricing model（交易 / 定价模型）
→ Membership Re-entry Review #1（会员重启检查 #1）
```

> Spatial Flow（商品 / 空间产品域）的实物商品交易不是“未来可能的商业模式”，而是已经成立的商业支柱。

## 1.2 Transaction Infrastructure（交易基础设施）不是 Monetization Model（商业模式）

以下能力虽然涉及金钱，但它们不是独立商业模式：

- Checkout（结账）；
- Payment（支付）；
- Crypto Payment（加密货币支付）；
- Order（订单）；
- Refund / Return（退款 / 退货）；
- Track Order（订单追踪）；
- Commerce Account（电商账户）；
- Customer Support（客户支持）。

例如：

> 支持 Crypto Payment（加密货币支付）

只能说明：

> 用户可以通过某种 Payment Rail（支付通道）完成交易。

不能说明：

> Project 3（项目三）多了一个新的 Revenue Model（收入模式）。

必须始终保持：

> Payment Rail（支付通道） != Monetization Model（商业模式）。

# 3. Round 11（第十一轮）已经出现一种“资金流”，但它不是用户付费产品

Round 11（第十一轮）已经确认 Commission（约稿）是 Editorial Acquisition Route（编辑获取路径）。

这可能意味着：

> Platform（平台） → Author / Creator（作者 / 创作者）支付稿酬。

这是：

> Editorial Cost / Creator Compensation（编辑成本 / 创作者报酬）

而不是：

> Reader Revenue（读者收入）。

这个区别非常重要。

Round 13（第十三轮）不能看到“钱”就全部归入 Monetization（商业化）。

Project 3（项目三）未来至少会同时存在：

- Revenue Inflow（收入流入）；
- Creator / Editorial Cost（创作者 / 编辑成本）；
- Commerce Operating Cost（电商运营成本）；
- Payment Processing Cost（支付处理成本）；
- Service Delivery Cost（服务交付成本）。

这些必须分开。

# 4. Ink & East（内容 / 知识产品域）与 Spatial Flow（商品 / 空间产品域）的三种关系模型

这是 Round 13（第十三轮）当前第一个真正需要用户参与的 Product Decision（产品决定）。

## Model A（模型 A）— Shared Platform + Distinct Product Domains（共享平台 + 独立产品域）

结构：

```text
Project 3（项目三）
├── Ink & East（内容 / 知识 / 编辑 / 社区产品域）
└── Spatial Flow（商品 / 空间 / 电商产品域）
```

可以共享：

- Account（账户）；
- Authentication（身份认证）；
- Identity（身份）；
- Search Infrastructure（搜索基础设施）；
- Saved / Follow Infrastructure（收藏 / 关注基础设施）；
- Notification Infrastructure（通知基础设施，未来若实现）；
- Support Infrastructure（支持基础设施）；
- Payment Infrastructure（支付基础设施）；
- Data / Analytics Infrastructure（数据 / 分析基础设施，按权限边界）。

但 Product Semantics（产品语义）保持分离：

- 买过商品 ≠ 更有文化权威；
- 买得多 ≠ Recommendation（自然推荐）更高；
- 买服务 ≠ Work Recognition（作品认可）；
- Editorial Selection（编辑选稿）不因消费金额变化；
- Commerce Conversion（商业转化）不反过来定义知识质量。

### 优点

- 最符合一个 Project 3（项目三）长期大平台的方向；
- 不复制两套 Account System（账户系统）；
- Spatial Flow（商品 / 空间产品域）可以正常承担商业收入；
- Ink & East（内容 / 知识产品域）保持编辑与知识可信度；
- 未来更换总品牌仍有空间。

### 风险

- Shared Platform（共享平台）必须做好 Domain Boundary（产品域边界）；
- Search（搜索）、Recommendation（推荐）、Profile（个人资料）、Saved（收藏）等共享能力不能把数据类型混成一团；
- Cross-link（跨域链接）必须克制，避免内容页变成商品导购页。

---

## Model B（模型 B）— Unified Commercial Surface（统一商业表面）

把 Ink & East（内容 / 知识产品域）与 Spatial Flow（商品 / 空间产品域）越来越强地融合：

- 内容；
- 商品；
- 服务；
- 推荐；
- 商业入口；

都围绕同一套商业转化组织。

### 优点

- 商业路径短；
- Cross-sell（交叉销售）容易；
- Marketing（营销）统一。

### 核心风险

这是我目前不建议的方向。

原因不是“商业不好”，而是 Product Semantics（产品语义）会开始污染：

```text
高转化内容
→ 得到更多展示
→ 看起来更重要
→ 商业表现反向影响编辑 / 推荐
```

最终容易破坏我们之前已经封存的：

- Recommendation（推荐）；
- Recognition（作品认可）；
- Editorial Curation（编辑策展）；
- Knowledge Authority（知识权威）；

之间的分离。

---

## Model C（模型 C）— Operational Separation（高度运营分离）

Ink & East（内容 / 知识产品域）与 Spatial Flow（商品 / 空间产品域）基本作为两个系统运行。

可能分别拥有：

- Account（账户）；
- Search（搜索）；
- Saved（收藏）；
- Support（支持）；
- Data（数据）；
- Navigation（导航）。

### 优点

- 边界最简单。

### 风险

- 与 Project 3（项目三）“长期统一源码平台”的方向冲突；
- 大量重复基础设施；
- 用户身份割裂；
- 后期总品牌统一更困难；
- 维护成本增加。

因此也不建议作为默认方向。

从现有 Product Architecture（产品架构）看，我建议：

> **Model A（模型 A）— Shared Platform + Distinct Product Domains（共享平台 + 独立产品域）**

但必须特别强调：

这不是：

> Ink & East（内容 / 知识产品域）和 Spatial Flow（商品 / 空间产品域）永远必须是两个独立品牌。

> 现在就决定最终 URL（网址）或 Navigation（导航）结构。

> 即使未来总品牌统一，**知识 / 编辑域与商品 / 商业域仍然必须保持不同语义。**

这和品牌名字是两个问题。

# 6. Cross-domain Relationship（跨产品域关系）应该允许什么

如果采用 Model A（模型 A），我认为可以允许：

### 6.1 Contextual Link（情境化链接）
例如内容讨论：

- 空间；
- 材料；
- 器物；
- 水晶；
- 家居；
- 香草；
- 传统物质文化；

可以自然链接到 Spatial Flow（商品 / 空间产品域）的相关商品或空间内容。

但必须明显区分：

> Editorial Reference（编辑引用）
与
> Commercial Recommendation（商业推荐）。

### 6.2 Shared Account（共享账户）

用户不应该为了读内容与买商品注册两个完全独立账户。

但：

> Commerce Profile（电商资料）
和
> Public Identity / Contributor Identity（公开身份 / 贡献者身份）

不是同一个对象。

例如收货地址不应该进入公开 Profile（个人资料）。

### 6.3 Shared Saved Infrastructure（共享收藏基础设施）

底层可以共享 Saved Object Framework（收藏对象框架）。

但用户界面可以按对象类型区分：

- Saved Article（收藏文章）；
- Saved Passage（收藏段落）；
- Saved Product / Wishlist（收藏商品 / 心愿单）。

不能因为技术上都叫 Saved（收藏），就把它们做成同一种产品对象。

### 6.4 Search Federation（联合搜索）

未来可以存在 Unified Search Entry（统一搜索入口）。

但结果需要 Typed Results（类型化结果）：

- Article（文章）；
- Work（作品）；
- Topic（主题）；
- Person（人物）；
- Product（商品）；
- Service（服务）。

不能让商品因为转化率高就压过知识结果。

# 7. Commercial Signal Firewall（商业信号防火墙）

这是 Round 13（第十三轮）我认为必须建立的一条硬边界。

Commerce Signal（商业信号）可以用于：

- 商品推荐；
- 库存预测；
- 购物体验；
- 订单支持；
- 商业分析。

但不能直接成为：

- Work Recognition（作品认可）证据；
- Contributor Qualification（贡献者资格）证据；
- Editorial Selection（编辑选稿）证据；
- Reviewer Trust（评审信任）；
- Governance Authority（治理权）；
- Organic Recommendation（自然内容推荐）的直接加权因素；
- Knowledge Authority（知识权威）的证明。

例如：

> 用户购买了很多风水相关商品

不能直接推导：

> 用户是风水专家。

同样：

> 一篇文章带来了很多商品销售

不能直接推导：

> 这篇文章质量更高 / 更值得被自然推荐。

# 8. Monetization（商业化）不应该只有一种模式

Round 13（第十三轮）目前不应该寻找一个“统一商业模式”。

更合理的是允许不同 Product Domain（产品域）使用不同模式：

### Physical Goods（实物商品）
```text
one-time transaction（一次性交易）
```

### Human / Custom Service（人工 / 定制服务）
如果重新验证成功，可能是：
```text
one-time fee（一次性收费）
project fee（项目制收费）
deposit + balance（定金 + 尾款）
```

### Membership（会员）
Round 12（第十二轮）继续：
```text
DEFERRED（暂缓）
```

### Editorial Commission（编辑约稿）
这是：
```text
platform cost（平台成本）
```
而不是 Reader Monetization（读者商业化）。

### Sponsorship / Advertising（赞助 / 广告）
当前：
```text
NOT AUTHORIZED（未授权）
```
